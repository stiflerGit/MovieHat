# Go documenting skill

## Do not document the "how"
When writing comments of a function/variable/type etc... Do not explain how a piece of code does something,

## Do not document self-explanatory un-exported functions
godoc only exports comments of exported functions, so for un-exported functions documentation is not mandatory.
Document un-exported function only when its purpose is not clearly self-explanatory.
Example: 
```go
func mapTMDBSearchMovieResponseToDomain(r *tmdb.SearchMovieResponse) moviesearch.SearchMoviesRet {
	...
}
```
There is no need to document this function as it is named `mapTMDBSearchMovieResponseToDomain` and it takes `*tmdb.SearchMovieResponse` and returns `moviesearch.SearchMoviesRet`. So it cleary map the input the output.

Instead, un-exported should be documented when their purpose is not clearly self-explanatory.
Example:
```go
// parsenum converts ASCII to integer.  num is 0 (and isnum is false) if no number present.
func parsenum(s string, start, end int) (num int, isnum bool, newi int) {
...
```
Here parsenum could mean anything. So we should document what this function does.

Another case in which is good to document un-exported functions is when they have particular edge cases.
Example:
```go
// The delete built-in function deletes the element with the specified key
// (m[key]) from the map. If m is nil or there is no such element, delete
// is a no-op.
func delete(m map[Type]Type1, key Type)
```
here what happens in case the key is not in the map 

## DO NOT document the how
Never document how a piece of code does something. Document the "WHAT" and eventually the "WHY"

Example: 
```go
// ScanError represents an error generated by the scanning software.
// It's used as a unique signature to identify such errors when recovering.
type ScanError struct {
	err error
}
```
ScanError represents an error generated by the scanning software. -> this is the what, i.e. what is this struct?
It's used as a unique signature to identify such errors when recovering. -> this is the why, i.e. why we have this struct?
It does by just wrapping an err so that ... -> this would be the how, i.e. how it does? But as you can see is not there because we never document how things are done.

Wrong Example:
```go
// Package tmdb implements the moviesearch domain over the TMDB HTTP API,
// using pkg/pagination to translate offset windows onto TMDB's fixed pages.
```
This is wrong as you can see because it says how the package does its job, i.e. by using pkg/pagination and translating offset windows onto TMDB's fixed pages.
Here the "WHAT", i.e. `// Package tmdb implements the moviesearch domain over the TMDB HTTP API` would be enough

## Always document exported types
Differently from unexported code, the exported one needs to be always documented, even if redundant.
Same example as before but this time the function is exported:
```go
// MapTMDBMovieDetailsResponseToDomain converts a validated TMDB movie details
// response into domain types.
func MapTMDBSearchMovieResponseToDomain(r *tmdb.SearchMovieResponse) moviesearch.SearchMoviesRet {
```
